Element: SE-02 Display client
Element profile: User-facing frontend (presentation only, no input)
Parent: System Design Concept
Status: Stable — no open TBCs remaining

Layout treatment is TO BE REFINED (SC-06 The projected layout is an open decision). This document specifies a baseline complete enough to build against, and marks each open decision explicitly.

Sections that apply. Goals, user interfaces, technical functions, outbound interfaces, entities, quality requirements, and constraints. Use cases are thin and unusual here: the element has one user type who does not interact with it. UC-01 An observer reads the projection is written anyway, because the element’s timing behaviour is only specifiable as a flow, and an absent use case section would read as an oversight rather than as a property of a non-interactive surface. Inbound technical interfaces do not apply.

Index / Solution Design Concept / System Design Concept / Display Client (SE-02)

Goals

G-01 Make turn-taking visible to people who are not participating

The element shall present visitor contributions and Sparring responses as paired exchanges, so that an observer sees a challenge and what provoked it rather than an isolated reply.
Success criteria (qualitative): An observer reading one projected item can tell that the AI declined to simply resolve the request.
Satisfies: SG-02 Make turn-taking readable from across the room

G-02 Remain populated at all times

The element shall never present an empty or near-empty surface while running, including before the first visitor of the day and between live sessions.
Success criteria (qualitative): The projection carries readable content continuously from start-up onward.
Satisfies: SG-06 Never present an empty surface

G-03 Stay readable and stable without attention

The element shall run for the duration of exhibition hours without reload, recover from backend interruption on its own, and update without visible redraw of unchanged content.
Success criteria (qualitative): No operator action is required at any point during opening hours. Unchanged items do not flicker or reflow on update.
Satisfies: SG-02 Make turn-taking readable from across the room, SG-06 Never present an empty surface
Rationale: SQR-02 The installation recovers without a person present. A projection that visibly redraws every few seconds reads as a status screen rather than as part of the work.

G-04 Distinguish concurrent visitors from one another

The element shall label each item so an observer can tell exchanges from different sessions apart, even when several appear in the same view.
Success criteria (qualitative): An observer looking at two items can tell whether they belong to the same visitor or different ones, without reading the content of either.
Satisfies: SG-02 Make turn-taking readable from across the room
Rationale: Readability (SG-02 Make turn-taking readable from across the room) previously meant "legible text" but not "distinguishable speaker" — every item carried the identical literal label "Visitor —", so two concurrent sessions were indistinguishable except by content. That gap is what this goal closes.

Use cases

UC-01 An observer reads the projection

Actors: UT-02 Observing visitor, SE-03 Backend service
Prerequisites: The element is running and has completed at least one successful retrieval.
Achieves: G-01 Make turn-taking visible to people who are not, G-02 Remain populated at all times, G-03 Stay readable and stable without attention, G-04 Distinguish concurrent visitors from one another
Realises: SSc-02

UT-02 Observing visitor performs no action in this use case. The steps describe the element’s own cycle, which is what determines what an observer sees at any moment.

  • ST-01-1 (Function-call) On a fixed interval, the element calls TF-01 Retrieve display material, which retrieves current display material from SE-03 Backend service.

  • ST-01-2 (Function-call) The element calls TF-02 Reconcile against what is displayed with the retrieved material. TF-02 Reconcile against what is displayed compares it against what is currently shown and determines what has changed.

  • ST-01-3 (Function-call) For each item that is new or changed, the element calls TF-03 Fit an item to the available space, which fits the item to the available space.

  • ST-01-4 (Activity) The element applies the changes, giving prominence to newly arrived material and receding older material. Unchanged items are left untouched.

  • ST-01-5 (User-interaction) UT-02 Observing visitor reads the surface. No input is available or expected.

Alternative scenarios

  • EX-01-1 (extends ST-01-1) Retrieval fails. The element retains what it is currently showing and retries on the next interval. Nothing on the surface indicates the failure, because an error message on a gallery wall is worse than slightly stale content. Outcome: Resume.

  • EX-01-2 (extends ST-01-2) The retrieved material is identical to what is shown. The element does nothing. Outcome: Terminate.

  • EX-01-3 (extends ST-01-1) Retrieval has failed continuously for a sustained period. The element continues showing its last material indefinitely rather than clearing. Resolved: no threshold, no action. The projector was never actually run at the exhibition (connectivity issues on-site), so this path never got exercised in practice. No threshold or operator alert was built, and none is judged worth building speculatively — a silent, indefinitely-stale wall is not a critical failure (the piece’s actual interaction is on the visitor’s own phone, SE-01 Input client; the wall is a bonus surface). Revisit only if a future exhibition actually runs the projection and this becomes a real operational problem. Outcome: Resume.

User interfaces

UI-01 Projection surface

User type: UT-02 Observing visitor
Realises: UC-01 An observer reads the projection

The whole projected area. No controls, no cursor, no navigation, no scroll. The surface is a fixed viewport whose contents change over time.

Baseline composition (agreed, build against this). TBC-01 Treatment of prominence and recency. currently adopts a masonry arrangement (column count per display profile — see C-03 Fixed target resolution, one of a set of named display profiles): each session is placed once into whichever column holds the fewest items, ties broken by least rendered height, and stays there for its lifetime. Every item has the same shape: a title line (the refined title, falling back to the scenario line — E-01.7 title/E-01.2 scenario), then a visitor contribution, then the Sparring response. One exchange pair per session, so each session contributes exactly one item.

Two properties of this baseline are settled and should not be revisited without a reason:

  • The exchange pair is the unit. A single turn shown alone conveys nothing about friction. The pair is the smallest thing that shows the mechanism.

  • Every item has the same shape. A design that renders the newest session differently from the rest requires two layouts, two truncation rules, and a decision about what happens when the newest session is unusually long. Uniformity removes all three. This is about shared template and truncation rule, not shared rendered height — height already varied with content length under the single-column baseline, and still does under masonry; that variance is what breaks ties between columns holding the same number of items, not a departure from uniformity.

A header above the wall carries the logo, a live clock, and a total session/exchange count. The clock is rendered entirely client-side from the system clock and the resolved locale — it reflects no backend data and needs no entity or interface entry of its own. The counts do come from SE-03 Backend service (E-02 Wall statistics) and are listed in Visible data below.

Open decisions

Source: SC-06 The projected layout is an open decision

Each was deliberately deferred until real pilot transcripts could be seen on HE-02 Projection setup at exhibition viewing distance. None of them changed the interface SE-03 Backend service provides, so they were resolved after the rest of the system worked. The exhibition has since run; all six are resolved below.

TBC-01 Treatment of prominence and recency. Resolved: masonry. Four candidates were considered; masonry shipped as the baseline and ran unchanged through the exhibition (venue display profile — 2 columns, 12-item limit, config.php). No pilot observation surfaced a reason to reconsider. The other three, for the record:

  • Size gradient. Newest item largest, older items progressively smaller and dimmer. Conveys accumulation well. Weakness: older items become texture rather than content, so most of the surface is not actually readable.

  • Rotation. One or two items at full size, cycling on a timer, with an indicator of how many others exist. Every item gets a turn at being readable. Weakness: loses the sense of accumulation, and requires a live-session priority rule so that a visitor who has just contributed sees their own exchange rather than waiting for the cycle.

  • Hybrid. A large primary region plus a thin strip of recent items. Retains both properties at the cost of more layout work.

  • Masonry (adopted, shipped). DISPLAY_COLUMNS columns (per display profile, config.php), each item placed once into the column holding the fewest items — ties broken by least rendered height — and never moved. Balancing by count first, height only as the tiebreaker: pure height-based placement skews badly whenever the number of items on the wall is below the columns' combined capacity and item heights vary, piling short items into one column and leaving the rest sparse. Every item stays equally readable (no gradient, no cycling), and filling the columns evenly gives a natural sense of accumulation without a timer. Weakness: strict global recency ordering is lost — a session’s column position no longer says "newer than everything below it," only "newer than what’s below it in its own column." Chosen for now because it needs no dwell-time rule (TBC-03 Dwell time, if any.) and no live-session interrupt rule (TBC-02 Whether a live session interrupts.), unlike rotation/hybrid.

    Masonry has its own version of "does everyone get seen," distinct from TBC-02 Whether a live session interrupts.: with the display profile’s item limit and selection by most-recent-activity (Store::getDisplayableSessions, ORDER BY last_active_at DESC), a session that goes quiet is excluded, not merely delayed — it can drop off the wall entirely if enough other sessions stay more active. Accepted as intentional: recency-eviction gives visitors a reason to keep engaging rather than submitting once and disengaging, which fits a piece about friction. Not revisited unless pilot observation shows visitors feeling unfairly dropped rather than prompted to continue.

TBC-02 Whether a live session interrupts. Resolved: not applicable. Only applicable if TBC-01 Treatment of prominence and recency. resolved to rotation or hybrid. It resolved to masonry instead, where the analogous question is answered above — no live-session interrupt rule was ever needed or built.

TBC-03 Dwell time, if any. Resolved: not applicable. Moot for the same reason as TBC-02 Whether a live session interrupts.: masonry items never rotate, so there is nothing to dwell on. No dwell-time constant exists in config.php.

TBC-04 Which exchange pair per session. Resolved: most recent, unchanged. Checked against the exhibition’s live data (49 sessions): most sessions never exceed one or two exchanges, so there is usually no alternative pair to choose from; in the sessions that ran three or more, Sparring’s pushback consistently sharpened with each turn rather than peaking early, so the most recent pair stayed the more demonstrative one. SE-03 Backend service keeps supplying it unchanged. (A related but distinct item stays open in TODO.md: suppressing a session’s first exchange from the wall when it is only the opening scenario prompt — a display-omission question, not a which-pair question, and doesn’t block this.)

TBC-05 Item count and truncation. Resolved: character bound. Fixed item count per display profile (itemLimit, config.php) plus a per-side character bound shipped and ran for the full exhibition. Rendered-height measurement was never needed.

TBC-06 Whether pilot-origin items are visually distinguishable. Resolved: left unmarked. Origin stays off the normal surface, visible only behind the operator debug flag (arena.js, QR-07 Diagnostic tag is available to an operator) — the "keep the surface uniform" option above.

Technical functions

TF-01 Retrieve display material

Detail level: Stepwise
Achieves: G-02 Remain populated at all times, G-03 Stay readable and stable without attention

  • FS-01-1 (Outbound-call) Call TO-01 Retrieve display material for current display material. Call behaviour: Synchronous, no retry within a cycle, timeout shorter than the polling interval so that requests cannot overlap. A failure is not escalated: the function returns the previous material unchanged. Consecutive failures are counted for TBC-03 Dwell time, if any. but trigger no action. Polling interval is 4 seconds (DISPLAY_POLL_INTERVAL_SECONDS, config.php).

  • FS-01-2 (Data-operation) Validate that the response has the expected shape. Discard it entirely if not, rather than rendering a partial surface.

  • FS-01-3 (Data-operation) Return the material for reconciliation.

Alternative flows

  • FA-01-1 (extends FS-01-1) Timeout, transport failure, or an unexpected status. Return the currently held material, increment the failure count, and take no other action. Grouping is intentional: the element’s response is the same for every failure mode. Outcome: Resume.

TF-02 Reconcile against what is displayed

Detail level: Stepwise
Achieves: G-03 Stay readable and stable without attention

Determines the minimum change needed, so that unchanged items are not redrawn. This function is the whole reason the projection does not flicker.

  • FS-02-1 (Entity-access) Read the currently displayed items from E-01 Displayed material.

  • FS-02-2 (Data-operation) Match retrieved items against displayed items by session identifier (E-01.1 sessionId).

  • FS-02-3 (Data-operation) Produce three sets: items to add, items whose content has changed, and items to remove. An item present in both with identical content appears in none of them.

  • FS-02-4 (Entity-access) Write the new set to E-01 Displayed material once the changes have been applied.

TF-03 Fit an item to the available space

Detail level: Narrative
Achieves: G-01 Make turn-taking visible to people who are not

Trims an item’s contribution and response so that the item occupies its allotted space without overflow, preserving enough of both halves that the exchange still reads as an exchange. Trimming only one side would leave a challenge with no visible provocation, which defeats G-01 Make turn-taking visible to people who are not. The initial approach is a character bound per side; rendered-height measurement is the fallback if that proves inadequate (TBC-05 Item count and truncation.).

TF-04 Render the surface

Detail level: Narrative
Achieves: G-04 Distinguish concurrent visitors from one another

Applies the reconciled changes to UI-01 Projection surface with transitions on entry, recession, and exit. All content from SE-03 Backend service is inserted as text, never as markup. Each item’s visitor alias is derived once from its session identifier (E-01.1 sessionId) at the point the item is first added — never recomputed on update, since the value is invariant for a given session and recomputing it would be pure waste.

The entry transition is restricted to opacity and transform, and applies only to a node TF-02 Reconcile against what is displayed placed in the add set — never to a node TF-02 Reconcile against what is displayed placed in the update set. A node in the update set instead gets a brief in-place pulse (also transform-only) on the same node, marking that its content changed without re-adding or moving it. Both are compositor-only, so neither an entering nor an updating item can shift or redraw any other item on the surface, which is what keeps this consistent with QR-02 Unchanged content does not redraw rather than in tension with it — QR-02 Unchanged content does not redraw protects other items from disturbance, not whether a changed item itself may carry a cue. A session occupies one node for its lifetime: only its first exchange goes through the add path; every exchange after that is an update to that same node. No sound accompanies this element: it runs unattended (QR-03 Runs unattended for the full opening period), with no user gesture available to unlock audio playback.

Technical interfaces (inbound)

None. No element calls this one. It is a leaf that only reads.

Technical interfaces (outbound)

TO-01 Retrieve display material

Statement: This interface obtains the set of sessions currently eligible for projection by calling the backend service (SE-03 Backend service). Used on every polling cycle.
Input: The display-profile identifier the element was loaded with (?d=<name> on the address; absent means the default profile), forwarded verbatim. This names which physical screen the request is for — it is not a selection, ordering, or prominence parameter. The profile-to-item-count mapping is resolved entirely in SE-03 Backend service (TI-04 Retrieve display material), so item selection remains a backend decision and this element still carries no policy (C-02 This element holds no selection or ordering policy).
Output: An ordered list of items, each carrying a session identifier, a scenario statement, an optional refined title, one visitor contribution, one Sparring response, an origin value, and a recency marker; alongside the list, a total session count (integer, E-02.1 sessionCount) and a total exchange count (integer, E-02.2 exchangeCount).
Error cases: Service unavailable. Malformed or unexpected response shape.
Authoritative spec: SE-03 Backend service element design, TI-04 Retrieve display material.

No Calls → PE- relation applies. This element reaches no partner element.

Quality requirements

QR-01 Readable at exhibition viewing distance (Usability)

Applies to: UI-01 Projection surface
Acceptance criteria (qualitative): A complete exchange is readable by a standing observer at the room’s typical viewing distance, verified on HE-02 Projection setup in the exhibition space before opening. Not verified in a browser window.
Supports: SQR-03 The projection is readable at exhibition viewing

QR-02 Unchanged content does not redraw (Usability)

Applies to: TF-02 Reconcile against what is displayed, TF-04 Render the surface
Acceptance criteria: An update that adds one item leaves every other item visually undisturbed. No full-surface repaint occurs on a polling cycle.
Supports: SQR-03 The projection is readable at exhibition viewing

QR-03 Runs unattended for the full opening period (Availability)

Applies to: The element overall
Acceptance criteria (qualitative): Runs for the duration of exhibition hours without reload, memory growth that degrades rendering, or accumulated state that requires clearing.
Supports: SQR-02 The installation recovers without a person present

QR-04 Backend interruption is invisible on the surface (Availability)

Applies to: TF-01 Retrieve display material
Acceptance criteria: A failed retrieval leaves the surface unchanged and produces no visible error. Recovery requires no reload.
Supports: SQR-02 The installation recovers without a person present, SQR-07 The installation degrades visibly rather than silently
Rationale: This deliberately departs from SQR-07 The installation degrades visibly rather than silently's general rule that failures should be visible. SQR-07 The installation degrades visibly rather than silently protects the participant, who needs to know why nothing is happening. An observer needs no such signal, and an error message projected on a gallery wall is a worse outcome than briefly stale content.

QR-05 Visitor content cannot alter the surface (Security)

Applies to: TF-04 Render the surface
Acceptance criteria: All content from SE-03 Backend service is inserted as text. No path renders it as markup.
Element specific: Yes
Rationale: This surface is public and unattended, so the consequence of an injection is a projected wall rather than one person’s phone.

QR-06 Fixed viewport, no scroll, no overflow (Compatibility)

Applies to: UI-01 Projection surface, TF-03 Fit an item to the available space
Acceptance criteria: Content never extends beyond the projected area at the target resolution. No scrollbar appears under any content length.
Element specific: Yes

QR-07 Diagnostic tag is available to an operator, hidden by default (Maintainability)

Applies to: UI-01 Projection surface
Acceptance criteria: An address flag appends a session id / origin tag to each item. Absent by default; no visitor-facing affordance exposes or hints at it.
Element specific: Yes
Rationale: Same operator need as SE-01 Input client QR-06 Diagnostic detail is available to an operator — see there.

QR-08 Entry and update motion respect a reduced-motion preference, and are switchable together (Usability/Accessibility)

Applies to: UI-01 Projection surface, TF-04 Render the surface
Acceptance criteria: Both the entry transition and the update pulse are suppressed when the OS-level reduced-motion preference is set, and both are turned off together by a single configuration switch, independent of every other element, with no code change. Suppressing either changes nothing else about TF-01 Retrieve display material/TF-02 Reconcile against what is displayed — an added or updated item still appears/updates, without the motion.
Element specific: Yes
Rationale: Mirrors SE-01 Input client QR-07 Motion respects a reduced-motion preference. Must be removable without becoming an accessibility regression or affecting QR-02 Unchanged content does not redraw's stability guarantee either way.

Constraints

C-01 Layout treatment is an open decision (Organisational)

Source: SC-06 The projected layout is an open decision.
Applies to: UI-01 Projection surface, TF-03 Fit an item to the available space, TF-04 Render the surface.
Acceptance criteria: The baseline in section 3 was implemented first, then run at the exhibition on HE-02 Projection setup. TBC-01 Treatment of prominence and recency. through TBC-06 Whether pilot-origin items are visually are all resolved.
Consequence: Rules out encoding a specific prominence treatment into TO-01 Retrieve display material's request or into SE-03 Backend service's response shape. The interface must serve any of the three candidates without change. (The display-profile identifier TO-01 Retrieve display material does carry is a screen id, not a prominence choice — see C-03 Fixed target resolution, one of a set of named display profiles.)
Implements: SC-06 The projected layout is an open decision

C-02 This element holds no selection or ordering policy (Technical)

Source: AP-01 All logic lives in the backend.
Applies to: TF-01 Retrieve display material, TO-01 Retrieve display material, E-01 Displayed material.
Acceptance criteria: The element renders what SE-03 Backend service returns, in the order returned. It performs no filtering, no sorting, and no eligibility assessment.
Consequence: Rules out client-side filtering of pilot material or of items the element judges unsuitable. Changing what appears is a backend change.
Implements: SC-01 PHP with a file-backed store on a single hosted

C-03 Fixed target resolution, one of a set of named display profiles (Technical)

Source: SC-03 Build effort is capped and the piece is expendable.
Applies to: UI-01 Projection surface.
Acceptance criteria: The element renders against one of a small set of named display profiles, each targeting a single fixed resolution with no responsive behaviour within it. The active profile is chosen at run time by an address parameter (?d=<name>), defaulting to the exhibition profile when the parameter is absent or unrecognised. A profile fixes three things: the resolution it targets, the masonry column count (DISPLAY_COLUMNS), and the number of items the element requests from SE-03 Backend service (see TO-01 Retrieve display material). Consequence: Rules out any framework requiring a build.
Implements: SC-03 Build effort is capped and the piece is expendable
