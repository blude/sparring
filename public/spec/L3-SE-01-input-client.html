Element: SE-01 Input client
Element profile: User-facing frontend
Parent: System Design Concept
Status: Stable — no open TBCs remaining

Sections that apply. All sections apply, with user interfaces and use cases as the core. Technical functions are thin by design: per AP-01 All logic lives in the backend, this element holds no generation, no moderation, and no session policy. Entities cover in-memory view state only, since nothing is stored on the device.

Index / Solution Design Concept / System Design Concept / Input Client (SE-01)

1. Goals

1.1. G-01 Reach a working input surface with nothing but a scan

The element shall present a usable input surface immediately on opening, with no installation, registration, or instruction step.
Success criteria (qualitative): A visitor who has never seen the piece submits their first contribution without asking anyone how it works.
Satisfies: SG-01 Start a session from a personal device with no

UI-01 Session surface shows a "Playbook" card of participation rules for a new/empty session (not a resumed one with prior turns). It’s visually an instruction step, but never gates the input surface — the field’s usability doesn’t depend on it, and it’s dismissed automatically by the visitor’s first submission rather than requiring an acknowledgement. Documented here as a deliberate, non-blocking exception rather than a silent one.
The page also declares a web app manifest (display: standalone, home-screen icon) so a visitor may install it — this is an opt-in a visitor reaches through their own browser chrome, never a step the flow prompts or requires, so it does not gate G-01 Reach a working input surface with nothing but a scan.

1.2. G-02 Hold the visitor’s place through interruption

The element shall restore a session and its exchanges after a reload, a locked device, or a backgrounded tab.
Success criteria (qualitative): Reloading restores the full session with no loss of prior exchanges and no repeated consent step.
Satisfies: SG-03 Survive interruption of the visitor’s session

1.3. G-03 Make waiting and failure legible

The element shall show that a response is being produced, and shall state plainly when one cannot be.
Success criteria (quantitative): An in-progress state appears within 300 ms of submission.
Satisfies: SG-04 Run unattended and absorb misuse without operator
Rationale: Several seconds of unexplained stillness in a gallery reads as a broken piece, not a thinking one.

1.4. G-04 Make unsuitable input visible

The element shall show that an input is invalid and should require the user to modify its content before sending again.
Rationale: Participants should be allowed to edit their input to fix the problem.

This is the authoritative behavior for unsuitable content — an earlier version of L2’s AP-05 Moderation gates storage, not a per-session display described the session ending instead; that reading is superseded (see L2 AP-05 Moderation gates storage, not a per-session display's own note on why).

1.5. G-05 Give the visitor a light identity, and a way to deliberately start over

The element shall reveal a generated nickname and avatar in the header once consent is recorded, and shall let the visitor abandon the current session and begin a fresh one on request.
Success criteria (qualitative): A visitor can find their own alias in the header at any point after consenting, and can start a new session from the same screen without navigating away manually.
Derived: Yes
Rationale: The alias/avatar follows from SE-02 Display client's G-04 Distinguish concurrent visitors from one another (display element design) — the wall now labels each session by a generated alias, so a visitor can recognise their own item on the shared surface only if the input client shows them the same value. The new-session control is a related convenience bundled into the same header for the same visitor. Neither was asked for by a stakeholder; both are a UX layer on top of the required consent gate.

1.6. G-06 Offer a light, always-skippable way to react to a finished session

The element shall present a short rating and open-feedback prompt when a session ends, and shall let the visitor leave without answering any part of it.
Success criteria (qualitative): Dismissing the prompt with nothing answered is exactly as available as answering it, from the visitor’s first look at it.
Satisfies: SG-09 Collect an optional visitor self-report at session

2. Use cases

2.1. UC-01 Begin a session

Actors: UT-01 Participating visitor, SE-03 Backend service
Prerequisites: None. This is the entry point.
Achieves: G-01 Reach a working input surface with nothing but a scan, G-05 Give the visitor a light identity
Realises: SSc-01

  • ST-01-1 (Function-call) On load, the element calls TF-01 Establish the session with the address contents. TF-01 Establish the session finds no session identifier and requests a new session, returning the identifier and an empty session.

  • ST-01-2 (Activity) The element places the identifier in the address without adding a history entry.

  • ST-01-3 (User-interaction) UI-01 Session surface presents the consent decision: agreement to take part, plus independent retention and projection choices. The contribution field is present but not usable.

  • ST-01-4 (User-interaction) UT-01 Participating visitor records their three decisions on UI-01 Session surface.

  • ST-01-5 (Function-call) The element calls TF-02 Record the consent decision with the three decisions. TF-02 Record the consent decision sends them to SE-03 Backend service and returns confirmation.

  • ST-01-6 (Activity) The element enables the contribution field. UC-02 Contribute a turn becomes available.

  • ST-01-7 (Function-call) The element calls TF-05 Derive visitor identity with the session identifier and reveals the resulting alias and avatar in the header. Never shown before this step — consent is what gates it, not the session’s existence.

Alternative scenarios

  • EX-01-1 (extends ST-01-1) Session creation fails. UI-01 Session surface states that the installation is not accepting sessions and offers a retry. Outcome: Terminate.

  • EX-01-2 (extends ST-01-4) UT-01 Participating visitor declines retention, projection, or both. The decision(s) are recorded as declined and the flow continues unchanged from ST-01-5 — these are real opt-outs, not preconditions. Nothing about the surface differs afterwards. Outcome: Alternative-success.

  • EX-01-3 (extends ST-01-4) UT-01 Participating visitor does not agree to take part. Unlike EX-01-2, the flow does not proceed to ST-01-5: the Confirm action stays disabled and the contribution field remains unusable. Outcome: Terminate.

2.2. UC-02 Contribute a turn

Actors: UT-01 Participating visitor, SE-03 Backend service
Prerequisites: UC-01 Begin a session completed, or UC-03 Resume an interrupted session completed.
Achieves: G-01 Reach a working input surface with nothing but a scan, G-03 Make waiting and failure legible
Realises: SSc-01

  • ST-02-1 (User-interaction) UT-01 Participating visitor enters a contribution in UI-01 Session surface's input field. The remaining character allowance is shown as they type.

  • ST-02-2 (User-interaction) UT-01 Participating visitor submits.

  • ST-02-3 (Activity) The element disables the input field and shows the in-progress state.

  • ST-02-4 (Function-call) The element calls TF-03 Submit a contribution with the session identifier and the contribution. TF-03 Submit a contribution submits it and returns the completed exchange.

  • ST-02-5 (Function-call) The element calls TF-04 Render the exchange history with the returned exchange, which appends it to the rendered history.

  • ST-02-6 (Activity) The element clears the in-progress state, empties and re-enables the input field, and scrolls the newest exchange into view.

Alternative scenarios

  • EX-02-1 (extends ST-02-4) SE-03 Backend service reports that the request limit has been reached. UI-01 Session surface states this and re-enables the field. The typed contribution is preserved. Outcome: Resume.

  • EX-02-2 (extends ST-02-4) SE-03 Backend service reports that the session has reached its turn limit. UI-01 Session surface presents the session as complete, leaves the field disabled, and calls TF-07 Present the session evaluation. The history remains readable underneath the prompt. Outcome: Terminate.

  • EX-02-3 (extends ST-02-4) SE-03 Backend service reports that no response could be produced. UI-01 Session surface states plainly that the installation cannot respond right now and re-enables the field with the contribution preserved. Outcome: Resume.

  • EX-02-4 (extends ST-02-4) The request does not complete within the element’s own wait bound. The element stops waiting and behaves as in EX-02-3. Outcome: Resume.

  • EX-02-5 (extends ST-02-4) SE-03 Backend service reports the contribution as flagged (unsuitable). UI-01 Session surface states that the message can’t be shown — with wording that varies by coarse category (personal information versus inappropriate content, see QR-06 Diagnostic detail is available to an operator) — and re-enables the field with the contribution preserved, same shape as EX-02-1/EX-02-3. The session itself is unaffected. Outcome: Resume.

2.3. UC-03 Resume an interrupted session

Actors: UT-01 Participating visitor, SE-03 Backend service
Prerequisites: A session identifier is present in the address.
Achieves: G-02 Hold the visitor’s place through interruption, G-05 Give the visitor a light identity
Realises: SSc-01

  • ST-03-1 (Function-call) On load, the element calls TF-01 Establish the session with the address contents. TF-01 Establish the session finds an identifier and fetches the existing session from SE-03 Backend service.

  • ST-03-2 (Function-call) The element calls TF-04 Render the exchange history with the returned exchanges, which renders the history.

  • ST-03-3 (Activity) The element restores the surface to its correct state: input enabled if the session is open, presented as complete if it has reached its limit. The consent decision is not asked again.

  • ST-03-4 (Function-call) If the consent decision was already recorded on an earlier visit, the element calls TF-05 Derive visitor identity and reveals the alias and avatar immediately, same as ST-01-7.

Alternative scenarios

  • EX-03-1 (extends ST-03-1) The identifier is unknown to SE-03 Backend service or has expired. The element discards it and continues as UC-01 Begin a session from ST-01-1. Outcome: Alternative-success.

  • EX-03-2 (extends ST-03-3) The identifier is known but the consent decision was never recorded (awaiting-decision). The element presents UI-01 Session surface's consent decision again, same as ST-01-3, and continues as UC-01 Begin a session from there. Outcome: Alternative-success.

2.4. UC-04 Start a new session deliberately

Actors: UT-01 Participating visitor
Prerequisites: UC-01 Begin a session or UC-03 Resume an interrupted session completed — a session, active or complete, is currently shown.
Achieves: G-05 Give the visitor a light identity, G-06 Offer a light, always-skippable way to react
Realises: SSc-01

  • ST-04-1 (User-interaction) UT-01 Participating visitor presses "New session" in the header.

  • ST-04-2 (User-interaction) The element asks UT-01 Participating visitor to confirm, stating that the current session will no longer be shown.

  • ST-04-3 (Function-call) On confirmation, the element calls TF-07 Present the session evaluation, which shows the evaluation prompt and returns once UT-01 Participating visitor answers or skips it.

  • ST-04-4 (Activity) The element opens the surface with no session identifier in the address, which begins UC-01 Begin a session from ST-01-1.

Alternative scenarios

  • EX-04-1 (extends ST-04-2) UT-01 Participating visitor does not confirm. Nothing changes and the current session continues undisturbed. Outcome: Terminate.

3. User interfaces

3.1. UI-01 Session surface

User type: UT-01 Participating visitor
Realises: UC-01 Begin a session, UC-02 Contribute a turn, UC-03 Resume an interrupted session, UC-04 Start a new session deliberately

A single scrolling surface. The exchange history occupies the upper region, the input field is anchored below it. There is no navigation, no menu, and no second view.

Presentation notes. The consent decision must be answerable without scrolling on a small phone, or it becomes an obstacle at the exact moment the visitor is deciding whether to engage at all. None of the three checkboxes is preselected: a preselected or visually dominant "accept" is a dark pattern and defeats the point of asking. This holds even for the participation checkbox, which is required to proceed — required is not the same as defaulted-on. The avatar and alias stay hidden through the consent decision itself; nothing about "who" a visitor is appears until they have agreed to take part. A brief motion/sound layer on the consent decision and on submission (QR-07 Motion respects a reduced-motion preference) is thematic flair matching the exhibition’s martial-arts framing — decorative, never a condition for proceeding.

4. Technical functions

4.1. TF-01 Establish the session

Detail level: Stepwise
Achieves: G-01 Reach a working input surface with nothing but a scan, G-02 Hold the visitor’s place through interruption

Determines whether a session already exists and produces one either way, so that the calling use case does not branch on it.

  • FS-01-1 (Data-operation) Read the session identifier from the address. If absent, continue at FS-01-3.

  • FS-01-2 (Outbound-call) Call TO-03 Retrieve a session with the identifier. On success, return the session and its exchanges, and stop. Call behaviour: Synchronous, single attempt, 10 second timeout. A not-found or expired response is not an error and continues at FS-01-3. A timeout or transport failure surfaces to the caller as a failure.

  • FS-01-3 (Outbound-call) Call TO-01 Open a session to create a session. Return the identifier and an empty exchange list. Call behaviour: Synchronous, two attempts with a 1 second delay between them, 10 second timeout per attempt. Exhausted attempts surface to the caller as a failure.

Alternative flows

  • FA-01-1 (extends FS-01-2) The identifier is unknown or expired. Discard it and continue at FS-01-3. Outcome: Resume.

4.2. TF-02 Record the consent decision

Detail level: Narrative
Achieves: G-01 Reach a working input surface with nothing but a scan

Sends the visitor’s three decisions — agreement to take part, retention, projection — to SE-03 Backend service via TO-01 Open a session and holds the returned confirmation in E-01 Session view state. Synchronous, two attempts, 10 second timeout per attempt. Exhausted attempts leave the session unopened and surface a failure, because opening the input field without a recorded decision would retain content the visitor never agreed to. A declined-participation response is not a transport failure and is handled separately (EX-01-3): the field simply stays unusable. On a successful decision, a one-time title-card animation plays (QR-07 Motion respects a reduced-motion preference) — purely presentational, no goal relation, and never a condition for the field becoming usable. If the address also carries a recognized opening-prompt identifier — a fixed set authored in code, one per QR code printed for the exhibition — a successful decision additionally triggers TF-03 Submit a contribution once, automatically, with the corresponding pre-authored text as the contribution, before the visitor has typed anything. An unrecognized or absent identifier takes no action; the field opens empty as usual.

4.3. TF-03 Submit a contribution

Detail level: Stepwise
Achieves: G-01 Reach a working input surface with nothing but a scan, G-03 Make waiting and failure legible

  • FS-03-1 (Data-operation) Trim the contribution and reject it locally if it is empty or exceeds the bound, without calling out.

  • FS-03-2 (Outbound-call) Call TO-02 Submit a contribution with the session identifier and the contribution. Call behaviour: Synchronous. No retry, because a retried submission risks producing a duplicate exchange and the visitor is watching. Wait bound is 25 seconds (SE01_WAIT_BOUND_SECONDS, config.php), kept above SE-03 Backend service's own 20-second generation bound (SQR-01 A Sparring response arrives, or its absence is visible) so the backend decides the outcome before the client times out first. On rate-limit, turn-limit, flagged-content, or generation-failure responses, return the reported condition to the caller rather than treating it as a fault. On timeout or transport failure, return a generation-failure condition.

  • FS-03-3 (Data-operation) Append the returned exchange to E-01 Session view state and decrement the remaining turn count.

Alternative flows

  • FA-03-1 (extends FS-03-2) Any reported condition is returned unchanged to the caller, which decides what UI-01 Session surface shows. Grouping is intentional: this function does not distinguish between them because it takes the same action for all. Outcome: Resume.

4.4. TF-04 Render the exchange history

Detail level: Narrative

Produces the visible history from E-01 Session view state. Visitor and Sparring contributions are visually distinguished. Content from SE-03 Backend service is inserted as text, never as markup, so that anything a visitor types cannot alter the surface. Submission and its outcome additionally carry a non-blocking presentational layer — a brief motion and sound cue on submit, and on a rejected/failed result — layered on top of this rendering, never gating it (QR-07 Motion respects a reduced-motion preference). No goal relation: this is presentation logic serving use cases that already reference the goals.

4.5. TF-05 Derive visitor identity

Detail level: Narrative
Achieves: G-05 Give the visitor a light identity

Computes a nickname and an avatar emoji as a pure function of the session identifier (E-01.1 sessionId) — no call to SE-03 Backend service, nothing written anywhere. The same derivation runs in SE-02 Display client, so a visitor’s alias reads identically wherever it appears. Consistent with AP-03 Session identity travels in the URL; no accounts: identity stays derived from what already travels in the address, never a new piece of state.

4.6. TF-06 Refine the session title

Detail level: Narrative

Once the first exchange completes (UC-02 Contribute a turn), the element calls TO-04 Refine a session title with the session identifier to request a refined title, and replaces the header’s default "Untitled" state with it when one comes back. Deliberately non-blocking and best-effort: it is not a step of UC-02 Contribute a turn's own sequence, carries no wait bound, and never gates the field or the response the visitor is watching for. Its failure (network, timeout, malformed response) is invisible rather than reported — the header simply stays "Untitled," unlike QR-02 Every failure produces a statement's failure-statement requirement, which is about the turn itself, not this. No goal relation: like TF-04 Render the exchange history, this is presentation logic layered on a use case that already references the goals.

4.7. TF-07 Present the session evaluation

Detail level: Narrative
Achieves: G-06 Offer a light, always-skippable way to react

The rating/feedback form itself is answered at most once per session — a flag kept in the browser (not E-01 Session view state, since it must survive nothing more than a reload of the same tab), set once Skip or Send actually completes it, not merely on being shown. UC-04 Start a new session deliberately calls this function on every "End session" press regardless, so a later press after the flag is set skips straight to the same confirmation — with the plain-thanks copy, as if Skip had just been pressed — rather than asking again or leaving unannounced. Every rating question and the open-feedback field are optional; a Skip action and a Send action are both available from the first moment the prompt is shown, and neither dismisses the prompt itself — both replace the form with a fixed confirmation message and two actions, differing only in which message and in what happens first. Skip calls nothing and shows a plain thanks. Send calls TO-05 Submit a session evaluation first, with whichever fields were filled in (possibly none), without waiting for the result — a failed submission is invisible to the visitor, matching TF-06 Refine the session title's best-effort treatment of a non-essential background call — then shows a confirmation that feedback was received. Either way, the confirmation carries the same two actions: "Start new session," which reopens UI-01 Session surface with no session identifier in the address (the same outcome UC-04 Start a new session deliberately reaches, without a round trip through the start screen), and "Go back to start," which leaves it, styled the same as the form’s own Skip action. This deliberate pause before either action, rather than dismissing immediately, is what gives Send’s background call time to actually reach the network before anything navigates away from under it. Which rating questions are offered, and how many points each scale has, is fixed in code ahead of time — a fixed set authored in code, same as TF-02 Record the consent decision's opening-prompt identifiers — and this function presents whatever set it’s given, deciding none of it itself.

5. Technical interfaces (inbound)

None. The element provides no interface to other elements. It is reached by a person opening a URL, which is not an inbound technical interface in the sense this section covers.

6. Technical interfaces (outbound)

6.1. TO-01 Open a session

Statement: This interface creates a session and records the consent decision by calling the backend service (SE-03 Backend service). Used for establishing a session before any contribution is possible.
Input: Three consent booleans — agreement to take part, retention, projection — required together on the decision call; all absent on the creation call.
Output: Session identifier, turn allowance, session state.
Error cases: Service unavailable. Malformed request. Declined to agree to take part — distinct from a malformed request, since the shape is valid but the value is a hard no.
Authoritative spec: SE-03 Backend service element design, TI-01 Open a session.

6.2. TO-02 Submit a contribution

Statement: This interface submits a visitor contribution and obtains the Sparring response by calling the backend service (SE-03 Backend service). Used for every turn after the session is open.
Input: Session identifier, contribution text.
Output: The completed exchange, updated remaining turn count, session state.
Error cases: Request limit reached. Session turn limit reached. Contribution flagged as unsuitable — the visitor edits and resubmits; the session is unaffected. Generation failed. Session unknown or expired. Contribution rejected as malformed or over-length.
Authoritative spec: SE-03 Backend service element design, TI-02 Submit a contribution.

6.3. TO-03 Retrieve a session

Statement: This interface fetches an existing session and its exchanges by calling the backend service (SE-03 Backend service). Used for restoring state after an interruption.
Input: Session identifier.
Output: Session state, turn allowance and remaining count, ordered exchanges.
Error cases: Session unknown or expired. Service unavailable.
Authoritative spec: SE-03 Backend service element design, TI-03 Retrieve a session.

6.4. TO-04 Refine a session title

Statement: This interface requests a short, refined title for a session’s first contribution by calling the backend service (SE-03 Backend service). Used once per session, after the first exchange completes.
Input: Session identifier.
Output: Refined title (string) — always a usable value when the call succeeds; SE-03 Backend service falls back to a trim-based title internally rather than ever returning failure for "couldn’t generate one" (see SE-03 Backend service TF-07 Refine a session title).
Error cases: Service unavailable. Session unknown. Malformed request. None of these are shown to the visitor (TF-06 Refine the session title) — the header simply keeps its default "Untitled" state.
Authoritative spec: SE-03 Backend service element design, TI-06 Refine a session title.

No Calls → PE- relation applies. This element reaches no partner element directly, per AP-01 All logic lives in the backend.

6.5. TO-05 Submit a session evaluation

Statement: This interface records whatever the visitor answered in the evaluation prompt by calling the backend service (SE-03 Backend service). Used once per session, from TF-07 Present the session evaluation's Send action.
Input: Session identifier, zero or more rating answers, optional open-feedback text.
Output: None consumed by the caller — TF-07 Present the session evaluation dismisses the prompt without waiting for a result.
Error cases: Service unavailable. Session unknown. Malformed request. None of these are shown to the visitor, same treatment as TO-04 Refine a session title's failure cases.
Authoritative spec: SE-03 Backend service element design, TI-07 Submit a session evaluation.

No Calls → PE- relation applies, same reason as TO-04 Refine a session title's.

8.7. QR-07 Motion respects a reduced-motion preference; every effect is individually switchable (Usability/Accessibility)

Applies to: UI-01 Session surface, TF-02 Record the consent decision, TF-04 Render the exchange history
Acceptance criteria: Every added animation (consent-decision title card, submit motion, rejection motion) is suppressed when the OS-level reduced-motion preference is set, without disabling submission or the consent decision itself. Sound is a separate signal — prefers-reduced-motion is a vestibular-motion preference and does not govern audio — and is instead gated solely by its own configuration switch. Each effect (title card, submit motion, rejection motion, sound) can be turned off independently by configuration, with no code change, and a single configuration switch turns all of them off at once. The title card plays once the consent decision is recorded, not on any submission, so it never overlaps QR-01 The in-progress state appears immediately's in-progress state — the two have no shared trigger.
Element specific: Yes
Rationale: TODO.md’s JUICYNESS requirement is explicitly presentational flair, not core functionality — it must be possible to remove without touching TF-01 Establish the session through TF-03 Submit a contribution, and must never become an accessibility regression.

The AI’s own reply language is a separate behavior (TF-03 Submit a contribution/prompt-level, see G-04 Match the visitor’s reply language turn by of SE-04 System prompt) that follows what the visitor types, not this setting.

Source: SC-05 Retention requires consent; projection requires.
