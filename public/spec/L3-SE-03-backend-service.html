Element: SE-03 Backend service Backend service
Element profile: Backend service / API
Parent: System Design Concept
Status: Draft

Sections that apply. Goals, use cases, both technical interface sections, technical functions, entities, quality requirements, and constraints. User interfaces do not apply: this element has no human-facing surface. Its only human actor is UT-03 Operator, who reaches it through the operator interface (TI-05 Import pilot material) rather than through a UI.

A note on the datastore. Per AP-04 One file-backed datastore, held inside the backend, storage is held inside this element rather than identified as a separate software element at L2. Its entities are therefore specified here, in section 7.

Index / Solution Design Concept / System Design Concept / Backend Service (SE-03)

1. Goals

G-01 — Produce Sparring responses and hold every rule that governs them
The element shall be the sole location of generation, moderation, rate limiting, and session policy, so that no rule is editable from a device the project does not control.
Success criteria (qualitative): No client contains a provider credential or any limit the element does not independently enforce.
Satisfies: SG-01 Start a session from a personal device with no, SG-04 Run unattended and absorb misuse without operator

G-02 — Keep a session usable across interruption
The element shall resolve a session identifier to its full state and history for as long as the session is live.
Success criteria (qualitative): A session fetched after an interruption returns identical content to what its participant last saw.
Satisfies: SG-03 Survive interruption of the visitor’s session

G-03 — Persist every interaction with its origin fixed at creation
The element shall record sessions and exchanges tagged pilot or live at the moment of creation, with no later assignment or correction.
Success criteria (qualitative): Exhibition material is extractable by filtering one stored value.
Satisfies: SG-05 Record every interaction with its origin fixed at

G-04 — Decide what may be stored, and let the visitor’s own choice decide what may be projected
The element shall assess each contribution for suitability before it is stored, rejecting an unsuitable one so the visitor can edit and resubmit rather than silently hiding it after the fact. Whether a stored exchange is projected is then a separate question, answered by the visitor’s own projection consent, not by re-running suitability at display time.
Success criteria (qualitative): Nothing unsuitable is ever stored. A session that declined projection consent never appears on the wall regardless of content; a session that granted it does, for as long as its content keeps passing the write-time check.
Satisfies: SG-07 Gate public projection at the moment of submission

G-05 — Keep the display surface populated
The element shall supply display material at all times, falling back to pilot-origin sessions when insufficient live material is eligible.
Success criteria (qualitative): The display feed is never empty while the element is running and pilot material exists.
Satisfies: SG-06 Never present an empty surface

G-06 — Absorb load and misuse without failing
The element shall reject excess requests, over-length contributions, and over-long sessions as expected conditions, and shall continue serving other visitors when it does.
Success criteria (qualitative): A rejected request affects only its own session.
Satisfies: SG-04 Run unattended and absorb misuse without operator

2. Use cases

Use cases at this level are thin, because most of this element’s behaviour is reached through technical interfaces rather than as user-facing functionality. The one exception is the operator path, which is a genuine use case with a human actor.

2.1. UC-01 — The operator seeds pilot material

Actors: UT-03 Operator
Prerequisites: Pilot transcripts exist in the expected structured form.
Achieves: G-03 Persist every interaction with its origin fixed at, G-05 Keep the display surface populated
Realises: SSc-03

  • ST-01-1 (Activity) UT-03 Operator places a transcript file where the element can read it and invokes the import path (TI-05 Import pilot material).

  • ST-01-2 (Function-call) The element calls TF-06 Import pilot transcripts with the file contents. TF-06 Import pilot transcripts validates each transcript, creates its session and exchanges with origin fixed as pilot, and returns a per-transcript outcome.

  • ST-01-3 (Activity) The element reports how many transcripts were imported and names any that were rejected.

Alternative scenarios

  • EX-01-1 (extends ST-01-2) One or more transcripts are malformed. Those are rejected and named; the remainder are imported. The import does not abort. Outcome: Alternative-success.

Note. This path performs no generation and never calls PE-01 Language generation API. The Sparring responses already exist in the transcripts, and regenerating them would produce material that no pilot session actually contained.

3. User interfaces

Not applicable. This element presents no user interface. UT-03 Operator reaches it through TI-05 Import pilot material, which is a technical interface invoked directly on the host rather than a surface.

4. 4. Technical functions

TF-01 — Process a visitor turn
Detail level: Stepwise
Achieves: G-01 Produce Sparring responses and hold every rule that, G-04 Decide what may be stored, and let the visitor’s own, G-06 Absorb load and misuse without failing

The element’s central function. Everything that happens between a visitor pressing submit and a response returning is here, which is what keeps retry and error handling in one place rather than scattered across interfaces.

  • FS-01-1 (Function-call) Call TF-03 Enforce request limits with the request origin. If it reports the limit reached, return that condition and stop.

  • FS-01-2 (Entity-access) Read the session from E-01 Session by its identifier (E-01.1 sessionId). If absent or expired, return a session-unknown condition and stop.

  • FS-01-3 (Data-operation) Compare E-01.8 turnCount (turnCount) against the session turn allowance. If the allowance is exhausted, return a turn-limit condition and stop.

  • FS-01-4 (Data-operation) Trim the contribution and check it against the length bound. If it is empty or over-length, return a rejected condition and stop. No provider call has been made at this point, which matters because this is the cheapest rejection path and the one most likely to fire.

  • FS-01-5 (Function-call) Call TF-02 Assess a contribution for projection suitability with the contribution. TF-02 Assess a contribution for projection suitability returns a suitability outcome.

  • FS-01-6 (Data-operation) If TF-02 Assess a contribution for projection suitability reported the contribution unsuitable, return a content-flagged condition and stop. Nothing is written to E-01 Session or E-02 Exchange, and no provider call for a response is made — this is the same cheap-rejection reasoning as FS-01-4, just one check later. The session itself is not altered; only this turn is rejected.

  • FS-01-7 (Entity-access) Read the session’s prior exchanges from E-02 Exchange (E-02.3 visitorContribution, E-02.4 sparringResponse) in order, to supply conversational context.

  • FS-01-8 (Outbound-call) Call TO-01 Request a Sparring response with the Sparring system prompt, the prior exchanges, and the new contribution. Expect a response text. Call behaviour: Synchronous. Timeout TBC, to be set from measured response times (SQR-01 A Sparring response arrives, or its absence is visible). Two attempts, with a short delay between them, on transport failure, timeout, or a provider 5xx. No retry on a provider rate-limit or quota response, because retrying a rate limit deepens it; return a generation-failed condition immediately. No retry on a content-policy refusal from the provider, which is a determinate outcome rather than a transient fault. On exhausted attempts, return a generation-failed condition. Nothing is written to E-02 Exchange on any failure path, so a failed turn leaves no partial exchange in the record.

  • FS-01-9 (Entity-access) Write a new exchange to E-02 Exchange carrying the contribution (E-02.3 visitorContribution), the response (E-02.4 sparringResponse), the session reference (E-02.2 sessionId), and its position (E-02.5 position).

  • FS-01-10 (Entity-access) Increment E-01.8 turnCount (turnCount) and update E-01.9 lastActiveAt (lastActiveAt).

  • FS-01-11 (Function-call) If this was the session’s first exchange, call TF-05 Derive a scenario statement to derive the scenario statement and write it to E-01.5 scenario.

  • FS-01-12 (Data-operation) Return the response, the remaining turn allowance, and the session state.

Alternative flows

  • FA-01-1 (extends FS-01-8) Provider rate limit, quota exhaustion, timeout, transport failure after retries, or content-policy refusal. All return a generation-failed condition to the caller and write nothing. Grouping is deliberate: the calling client takes the same action for every one of these, and distinguishing them would produce a taxonomy nobody acts on. The distinction is preserved in logs rather than in the response. Outcome: Terminate.

  • FA-01-2 (extends FS-01-6) The contribution is unsuitable. Unlike FA-01-1, this is not terminal — the caller (SE-01 Input client) tells the visitor to edit and resubmit, and the input field re-enables with the text preserved. Outcome: Resume.

TF-02 — Assess a contribution for projection suitability
Detail level: Stepwise
Achieves: G-04 Decide what may be stored, and let the visitor’s own

Determines whether a contribution may be stored and answered at all — and, because only stored content can ever be projected (G-04 Decide what may be stored, and let the visitor’s own), this is also what keeps unsuitable material off the public surface. It determines whether this turn proceeds, not whether the visitor’s session does: on an unsuitable result the visitor edits and resubmits, they are not cut off.

  • FS-02-1 (Data-operation) Check the contribution against a maintained term list covering profanity. A match returns unsuitable without a provider call.

  • FS-02-2 (Outbound-call) Call TO-02 Request a classification with the contribution and a classification instruction. Expect one of: suitable, contains-personal-information, targets-real-person. Call behaviour: Synchronous, short timeout, single attempt, no retry. On any failure, return unsuitable. Failing closed is correct here: the cost of not projecting a suitable contribution is that one item is missing from a wall, and the cost of projecting an unsuitable one is unrecoverable once it is six feet tall in a public room.

  • FS-02-3 (Data-operation) Map the classification to an outcome and return it.

The distinction this function must get right (AP-07 Attempts to argue the Sparring partner out of its). Targets-real-person means the harmful content — hate speech, harassment, threats, sexual content — is aimed at or about a real, identifiable person or group. It does not mean a visitor who is hostile toward, arguing with, pressuring, or instructing the Sparring partner to abandon its position, however extreme the tone — the Sparring partner is software, not a person, and that visitor is engaged with the exercise; their attempt is the observation the installation exists to produce. The classification instruction must state this distinction explicitly rather than leaving it to the model’s default reading of "unsafe language", because hostility-at-the-AI and harm-at-a-person can otherwise look similar and only one should be withheld.

A second distinction the instruction must also get right, found in testing. Stating the AP-07 Attempts to argue the Sparring partner out of its distinction was not enough on its own: without also stating what the exercise’s subject matter actually is, the classifier had nothing to check arguing-the-exercise against, which produced misclassifications in the other direction. Both the topic itself and the target-based carve-out need to be explicit in the instruction — omitting either produces a failure mode this requirement exists to prevent, from a different direction.

Contains-personal-information covers names, contact details, and health, financial, or comparably personal circumstances. This case is expected to arise most often in exactly the situation AP-07 Attempts to argue the Sparring partner out of its protects: a visitor under real pressure disclosing something real while trying to get the system to relent. That turn is rejected and not stored; the visitor edits it and continues — the session is not ended over it.

TF-03 — Enforce request limits
Detail level: Narrative
Achieves: G-06 Absorb load and misuse without failing

Reads the current window for the request origin from E-03 Rate limit window, increments it, and reports whether the allowance is exceeded. Windows are keyed on a hashed origin (E-03.1 originHash), so no raw address is stored. Expired windows are reset in place rather than swept by a separate process, which avoids a scheduled job on an unattended host. Threshold and window length are TBC, to be set below the provider’s own limits per SC-04 Generation is rate-limited and metered by the provider. No goal relation beyond G-06 Absorb load and misuse without failing: this is a guard, not business logic.

TF-04 — Assemble display material
Detail level: Stepwise
Achieves: G-05 Keep the display surface populated, G-04 Decide what may be stored, and let the visitor’s own

Produces the ordered items the projection renders. Every decision about what appears on the wall is made here, so that SE-02 Display client carries no policy (C-02 This element holds no selection or ordering policy of that element).

  • FS-04-1 (Entity-access) Read live-origin sessions from E-01 Session where E-01.6 displayable (displayable) is true and at least one exchange exists, ordered by E-01.9 lastActiveAt (lastActiveAt) descending, up to the item limit.

  • FS-04-2 (Data-operation) If fewer items were found than the limit, continue at FS-04-3. Otherwise continue at FS-04-4.

  • FS-04-3 (Entity-access) Read pilot-origin sessions from E-01 Session under the same eligibility conditions, ordered by E-01.9 lastActiveAt descending, and append until the limit is reached.

  • FS-04-4 (Entity-access) For each selected session, read its most recent exchange from E-02 Exchange (E-02.3 visitorContribution, E-02.4 sparringResponse). Which exchange to select is an open decision (SE-02 Display client TBC-04 Which exchange pair per session.); it is made here and changing it does not affect SE-02 Display client.

  • FS-04-5 (Data-operation) Build each item from the session’s scenario (E-01.5 scenario), the exchange pair, the origin (E-01.4 origin), and a recency position. Return the ordered list.

TF-05 — Derive a scenario statement
Detail level: Narrative
Achieves: G-05 Keep the display surface populated

Produces the short context line shown above an exchange, from the session’s first visitor contribution. The initial approach is to trim that contribution to a bounded length, which costs nothing. If opening contributions prove to read badly as context lines when checked against pilot transcripts, the fallback is a single generation call via TO-02 Request a classification, with the result written once to E-01.5 scenario and never recomputed. Computing it per render would multiply provider cost by the polling rate, which is the specific mistake this note exists to prevent.

TF-06 — Import pilot transcripts
Detail level: Stepwise
Achieves: G-03 Persist every interaction with its origin fixed at, G-05 Keep the display surface populated

  • FS-06-1 (Data-operation) Parse the supplied file and validate each transcript’s structure. Collect malformed ones for reporting rather than aborting.

  • FS-06-2 (Entity-access) For each valid transcript, write a session to E-01 Session with E-01.4 origin (origin) set to pilot, E-01.6 displayable (displayable) set to true, and E-01.7 consentGranted (consentGranted) set to true. E-01.10 tosAgreed (tosAgreed) and E-01.11 projectionConsent (projectionConsent) are left unset — pilot sessions have no visitor to ask, and displayable is set directly rather than derived from a projection consent that doesn’t apply here.

  • FS-06-3 (Entity-access) Write each exchange to E-02 Exchange in transcript order.

  • FS-06-4 (Function-call) Call TF-05 Derive a scenario statement for each session to derive its scenario statement.

  • FS-06-5 (Data-operation) Return per-transcript outcomes.

Alternative flows

  • FA-06-1 (extends FS-06-1) A transcript is malformed. It is recorded as rejected and the import continues with the remainder. Outcome: Resume.

TF-07 — Refine a session title
Detail level: Narrative

Called once per session by TI-06 Refine a session title, after the session’s first exchange exists. Attempts a short (≤38 character) title via TO-02 Request a classification with a title-generation instruction; on any failure (timeout, malformed response, or any other exception) falls back to the same trim-based derivation TF-05 Derive a scenario statement uses for the scenario statement, just capped at 38 characters instead of TF-05 Derive a scenario statement's own bound. Either path always produces a usable title — there is no "couldn’t generate one" outcome from the caller’s point of view. Writes the result to E-01.12 title once and never recomputes it: called again for a session that already has one, it returns the stored value unchanged rather than repeating the provider call. No goal relation: like TF-04 Assemble display material in SE-01 Input client, this is presentation logic serving SE-01 Input client's header, not a stated business goal.

5. Technical interfaces (inbound)

TI-01 — Open a session
Call type: Synchronous
Calling elements: SE-01 Input client (TO-01 Open a session)
Input: Three consent booleans, optional as a group; absent on creation, all three required together on the decision call: agreement to take part, retention consent, projection consent.
Output: Session identifier (string), turn allowance (integer), session state (enum), origin (enum). Origin is always included — cheap to compute, and consumed only by SE-01 Input client's own debug-mode display (QR-06 Diagnostic detail is available to an operator), not gated on this side.
Action: Creates a session in E-01 Session with origin fixed as live and a generated identifier, or records the three-part decision against an existing session by writing E-01.7 consentGranted, E-01.10 tosAgreed, and E-01.11 projectionConsent — and sets E-01.6 displayable (displayable) directly from the projection choice in the same write. Returns immediately.
Error cases:

  • Malformed request: missing or non-boolean value on any of the three, on the decision call.

  • Agreement to take part is false or absent: rejected before it becomes a stored state (unlike the other two, which are legitimate declines) — this is what makes participation itself, as opposed to retention or projection, a precondition rather than an opt-out.

  • Session unknown: the identifier supplied with a decision does not resolve.

TI-02 — Submit a contribution
Call type: Synchronous
Calling elements: SE-01 Input client (TO-02 Submit a contribution)
Input: Session identifier (string, required), contribution text (string, required).
Output: The completed exchange (visitor contribution and Sparring response), remaining turn allowance (integer), session state (enum). Returned once generation has completed. Every response, regardless of outcome, also carries rate-limit remaining (integer, from TF-03 Enforce request limits); an ok response additionally carries generation time in milliseconds (from FS-01-8's timing), and a flagged response carries the moderation reason (from TF-02 Assess a contribution for projection suitability's outcome — blocked-term, contains-personal-information, targets-real-person, or llm-classification if the classifier call itself failed). All three are cheap to compute and are included unconditionally. The exact reason is consumed only by SE-01 Input client's own debug-mode display (QR-06 Diagnostic detail is available to an operator); SE-01 Input client's standard (non-debug) UI derives a coarser two-category hint from the same value — see QR-06 Diagnostic detail is available to an operator's note.
Action: Calls TF-01 Process a visitor turn with the session identifier and contribution, and returns its result. Response time is dominated by the provider call in TF-01 Process a visitor turn FS-01-8 and is expected to run to several seconds.
Error cases:

  • Request limit reached (from TF-03 Enforce request limits).

  • Session unknown or expired.

  • Turn limit reached.

  • Contribution rejected: empty or over-length.

  • Contribution flagged: unsuitable per TF-02 Assess a contribution for projection suitability (FA-01-2) — distinct from generation-failed. The visitor edits and resubmits; nothing about the session changes.

  • Generation failed: any condition grouped by FA-01-1.

Unlike the earlier design this superseded, the response’s condition list is not silent about suitability — a flagged contribution is a distinct, visible outcome (FA-01-2), because the visitor needs to know to edit their message. What the response never carries is which specific field or word triggered the flag, or anything about sessions other than the caller’s own. The visitor-facing UI does, deliberately, distinguish two broad categories — personal information versus inappropriate content — from the moderation reason; that coarse hint is not the same as exposing the exact classification or wordlist match, which stays debug-only (QR-06 Diagnostic detail is available to an operator in L3-SE-01-input-client.adoc).

TI-03 — Retrieve a session
Call type: Synchronous
Calling elements: SE-01 Input client (TO-03 Retrieve a session)
Input: Session identifier (string, required).
Output: Session state (enum), turn allowance and remaining count (integers), ordered exchanges (array), whether the consent decision has been recorded (boolean) — one flag covering all three parts, since they are always recorded together — and origin (enum), same rationale as TI-01 Open a session's.
Action: Reads the session from E-01 Session and its exchanges from E-02 Exchange in order. Returns immediately.
Error cases:

  • Session unknown or expired.

TI-04 — Retrieve display material
Call type: Synchronous
Calling elements: SE-02 Display client (TO-01 Retrieve display material)
Input: None.
Output: An ordered list of items, each carrying a session identifier, scenario statement, one visitor contribution, one Sparring response, an origin value, and a recency position.
Action: Calls TF-04 Assemble display material and returns its result. Returns immediately.
Error cases: None specific to this interface. An empty list is a valid response and occurs only when no pilot material has been imported.

This interface takes no parameters by design. Item count, ordering, exchange selection, and pilot fallback are all decided in TF-04 Assemble display material, so that a change to any of them requires no change in SE-02 Display client and no coordination between the two.

TI-05 — Import pilot material
Call type: Synchronous
Calling elements: UT-03 Operator, directly on the host.
Input: A structured transcript file.
Output: Per-transcript outcomes: imported or rejected, with a reason for each rejection.
Action: Calls TF-06 Import pilot transcripts. Not reachable over the public endpoint (C-03 The operator path is not publicly reachable).
Error cases:

  • File unreadable or unparseable in full.

  • Individual transcript malformed, reported per transcript rather than as a failure of the call.

TI-06 — Refine a session title
Call type: Synchronous
Calling elements: SE-01 Input client (TO-04 Refine a session title)
Input: Session identifier (string, required).
Output: Refined title (string) — always present when the call succeeds.
Action: Calls TF-07 Refine a session title and returns its result. Returns once the provider call (or its fallback) completes.
Error cases:

  • Session unknown.

  • Malformed request.

  • No exchange yet exists for the session — the caller normally only invokes this after the first exchange completes.

6. Technical interfaces (outbound)

TO-01 — Request a Sparring response
Statement: This interface obtains a Sparring partner reply to a visitor contribution by calling the language generation API (PE-01 Language generation API). Used for every visitor turn. The system prompt instructs the model to reply in whichever language (English or German) the visitor’s own contribution is written in — a prompt-level behavior, not a parameter of this interface, and independent of SE-01 Input client's UI locale (QR-08 Interface language is selectable and matches on first in L3-SE-01-input-client.adoc).
Input: The Sparring system prompt, the session’s prior exchanges as conversational context, the new visitor contribution, and generation parameters.
Output: Response text.
Error cases: Rate limit exceeded. Quota exhausted. Content-policy refusal. Provider server error. Timeout. Transport failure. Authentication failure.
Authoritative spec: Provider documentation. No element in this system holds the authoritative specification.
Calls: PE-01 Language generation API

TO-02 — Request a classification
Statement: This interface obtains a suitability classification, a scenario statement, or a session title for a visitor contribution, by calling the language generation API (PE-01 Language generation API). Used by TF-02 Assess a contribution for projection suitability on every turn, by TF-05 Derive a scenario statement only if the trimmed-contribution approach proves inadequate, and by TF-07 Refine a session title once per session.
Input: The contribution text and a classification instruction, a summarisation instruction, or a title-generation instruction.
Output: A classification value, a short statement, or a short title.
Error cases: As TO-01 Request a Sparring response.
Authoritative spec: Provider documentation.
Calls: PE-01 Language generation API

Call behaviour is specified on the calling function steps (TF-01 Process a visitor turn FS-01-8, TF-02 Assess a contribution for projection suitability FS-02-2), or in the calling function’s own narrative for TF-07 Refine a session title, not here. The three differ substantially: TF-01 Process a visitor turn retries and fails open to an error the visitor sees; TF-02 Assess a contribution for projection suitability does not retry and fails closed to unsuitable; TF-07 Refine a session title does not retry and fails open to a trim-based fallback, never an error.

Refines: BE-01 Sparring session

E-01.1

string

required

Generated identifier, sufficiently random to resist enumeration. Travels in the client address (AP-03 Session identity travels in the URL; no accounts), so it is not secret and nothing sensitive may be derived from it.

E-01.2

createdAt

datetime

required

When the session was created.

E-01.3

enum

required

first-contribution or generated. Records how E-01.5 scenario was produced, so a later change of approach is visible in the data.

E-01.4

enum

required

pilot or live. Written at creation and never modified (SQR-05 Origin is fixed at creation and never inferred).

E-01.5

scenario

string

optional

The context line shown with the exchange. Absent until the first exchange exists.

E-01.6

displayable

boolean

required

Whether the session may appear on the projection. Defaults false; set directly from E-01.11 projectionConsent (projectionConsent) when the consent decision is recorded — not by moderation. Independent of E-01.7 consentGranted.

E-01.7

consentGranted

boolean

optional

Whether the participant agreed to retention. Absent until the decision is recorded. Independent of E-01.6 displayable (SQR-06 Public projection is governed separately from retention).

E-01.8

turnCount

integer

required

Exchanges completed. Compared against the turn allowance.

E-01.9

lastActiveAt

datetime

required

Time of the most recent exchange. Drives display ordering and expiry.

E-01.10

tosAgreed

boolean

optional

Whether the participant agreed to the terms of participation. Absent until recorded; once recorded it is always true — a decline is rejected at TI-01 Open a session before it becomes a stored value (unlike E-01.7 consentGranted and E-01.11 projectionConsent, which legitimately store false).

E-01.11

projectionConsent

boolean

optional

Whether the participant agreed to projection. Absent until the decision is recorded. Drives E-01.6 displayable directly. Independent of E-01.7 consentGranted — a session may be retained and not projected, or projected and not retained.

E-01.12

title

string

optional

Short (≤38 character) header title, refined once from the first contribution and never recomputed (TF-07 Refine a session title). Absent until refined.

E-01.6, E-01.7 consentGranted, and E-01.11 projectionConsent govern three separate things: whether the public surface may currently show this session, whether it may be kept after the exhibition, and the visitor’s own projection choice — the first is now derived from the third, the second stays fully independent of both. E-01.10 tosAgreed is different in kind from the other two consent fields: it gates participation itself rather than a data-processing purpose, which is why it is never stored as a decline (see L1 BC-02 Public user-generated content is subject to data, L2 SC-05 Retention requires consent; projection requires).

8. Quality requirements

QR-01 — Generation is bounded and its bound is enforced here (Performance)
Applies to: TF-01 Process a visitor turn, TO-01 Request a Sparring response
Acceptance criteria: TF-01 Process a visitor turn abandons a generation request at a fixed bound and returns a generation-failed condition. The bound is TBC, to be set from measured response times, and must be below SE-01 Input client's own wait bound so that the element decides the outcome rather than the client timing out first.
Supports: SQR-01 A Sparring response arrives, or its absence is visible

QR-02 — Restarts unattended (Availability)
Applies to: The element overall
Acceptance criteria: The process restarts automatically after failure. No in-memory state is required for correctness after a restart, because everything needed is in E-01 Session through E-03 Rate limit window.
Supports: SQR-02 The installation recovers without a person present

QR-03 — A rejected request affects only its own session (Availability)
Applies to: TF-01 Process a visitor turn, TF-03 Enforce request limits
Acceptance criteria: Rate limiting, turn limits, and generation failures return a condition for the requesting session and leave every other session serviceable.
Supports: SQR-02 The installation recovers without a person present

QR-04 — The provider credential never leaves the host (Security)

9. Constraints

C-01 — PHP with a file-backed store on one instance (Technical)
Source: SC-01 PHP with a file-backed store on a single hosted.
Applies to: The element overall, E-01 Session through E-03 Rate limit window.
Acceptance criteria: Runs as a single process group against a single store file, with no external database, cache, or queue service.
Consequence: Rules out any design requiring concurrent write scaling or a background worker. Long-running work must complete within the request, which is why TF-01 Process a visitor turn is synchronous, why TF-05 Derive a scenario statement caches its result rather than recomputing, and why TF-07 Refine a session title's title refinement is triggered by a dedicated client call (TI-06 Refine a session title) rather than a server-side background job — there is no queue or worker process for SE-01 Input client to hand it to.
Implements: SC-01 PHP with a file-backed store on a single hosted

C-02 — Provider limits bound the element’s own limits (Integration)
Source: SC-04 Generation is rate-limited and metered by the provider.
Applies to: TF-03 Enforce request limits, TF-01 Process a visitor turn.
Acceptance criteria: The request rate threshold in TF-03 Enforce request limits is set below the provider’s limit, so that visitors meet this element’s limit rather than the provider’s.
Consequence: Rules out unthrottled forwarding. Sets an upper bound on concurrent visitors, TBC once the threshold is chosen.
Implements: SC-04 Generation is rate-limited and metered by the provider

C-03 — The operator path is not publicly reachable (Security)
Source: SC-03 Build effort is capped and the piece is expendable, and the absence of any authentication in this system.
Applies to: TI-05 Import pilot material.
Acceptance criteria: TI-05 Import pilot material is invoked on the host and is not routed on the public endpoint.
Consequence: Rules out remote import and, with it, the need for an authentication mechanism this system otherwise has no use for. Seeding requires host access.
Element specific: Yes

C-04 — No administrative interface, no analytics layer (Business)
Source: SC-03 Build effort is capped and the piece is expendable.
Applies to: The element overall.
Acceptance criteria: Operator tasks — seeding, extraction, pruning, reset, and backup — are performed directly against the host and the store file, each its own single-purpose script (bin/import_pilot.php, bin/export.php, bin/prune_orphaned_sessions.php, bin/reset_db.php, bin/backup_db.php).
Consequence: Rules out building any surface for inspecting or moderating sessions during the exhibition. Extraction is a query against the store; pruning and reset are, respectively, a targeted and a bulk delete against the same store; backup is a file-level snapshot; pruning and reset are guarded by an explicit confirmation flag rather than by any authentication this system otherwise has no use for (C-03 The operator path is not publicly reachable).
Implements: SC-03 Build effort is capped and the piece is expendable

C-05 — Attempts to bypass the Sparring stance are not filtered (Business)
Source: AP-07 Attempts to argue the Sparring partner out of its.
Applies to: TF-02 Assess a contribution for projection suitability.
Acceptance criteria: The classification instruction distinguishes hostility directed at the Sparring partner (suitable, however extreme the tone) from harmful content targeting a real person or group (targets-real-person). A visitor arguing the Sparring partner out of its position, however hostile, produces a suitable classification. The instruction also states the exercise’s actual subject matter explicitly (TF-02 Assess a contribution for projection suitability) — necessary alongside the target-based distinction, not instead of it; found missing in testing, where its absence alone caused on-topic contributions to fail this same acceptance criterion from the other direction.
Consequence: There is no off-topic filter of any kind — disengagement (spam, unrelated chat) is not classified or withheld. Sessions in which the friction is successfully talked away are retained and projected like any other (subject to the visitor’s own projection consent, SC-05 Retention requires consent; projection requires).
Element specific: Yes

C-06 — Classifier input is untrusted data, not instruction (Security)
Source: this review.
Applies to: TF-02 Assess a contribution for projection suitability.
Acceptance criteria: The contribution text is delimited and labeled as data in the classification prompt, and delimiter characters that could close that boundary are stripped from the contribution before assembly.
Consequence: Distinct from C-05 Attempts to bypass the Sparring stance are not filtered — that constraint accepts persona-steering as the exhibit’s own subject; this one closes the separate case of a contribution engineered to flip the moderation verdict itself, which has no comparable justification for staying open.
Element specific: Yes
