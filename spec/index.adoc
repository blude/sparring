== What Sparring is

Sparring is an exhibition object built for a master's thesis at FH Dortmund. A
QR code on the wall opens a plain text field on the visitor's phone. Whatever
they type goes to an AI that argues back instead of answering, and both sides
of the exchange show up on a wall behind them, so a room full of people
watches one visitor get pushed to reason through their own argument. It runs
for three days at Superraum in Dortmund. The subject is Digital Design
education, and the AI plays a motivated sparring partner rather than a helpful
chatbot.

These documents are the design record. They describe what has to be true about
the installation and why, not how the code is written.

== How to read this

The documentation follows a three-layer framework: Solution, System, and
Element design. Each layer answers a narrower question than the one above
it, and every item carries an ID (`BG-01`, `SE-03`, `TF-02`) so a decision at
one layer traces back to the need it satisfies one layer up. A Digital
Design Brief sits above the three layers, and a System Realization record
sits below them.

[cols="1,4"]
|===
| L0: Digital Design Brief | A concise, high-level summary of a planned initiative, written for management. Enough to make a Go/No-Go decision without the technical detail. It sits above the three layers.
| L1: Solution | Why build it. Business goals, the value it creates, the processes around it. Non-technical.
| L2: System | The installation as one system. System goals, architecture, the elements it breaks into, and scenarios that run end to end.
| L3: Element | One document per element. The behaviour, interfaces, and constraints of each piece L2 named.
| LX: Realization | The deployment reality: server sizing, PHP version, SSL, and diagrams at implementation detail. It sits below the three layers.
|===

This project has no L0. A Design Brief exists so management can make a
Go/No-Go call on a significant investment, with stakeholders aligning before
budget gets committed. Sparring is a one-person thesis prototype with a
single exhibition run, and its requirements came from the thesis proposal
itself. There's no approval gate to clear, and no other stakeholder who
needs to sign off. The record starts at L1, and its constraints trace to
nothing above them.

== Specification documents

* xref:L1-solution-design-concept.adoc[L1: Solution Design Concept] holds the future press release, the business goals, and the value proposition behind arguing with an AI in public. Start here.
* xref:L2-system-design-concept.adoc[L2: System Design Concept] covers the system goals, the architecture diagram, the split into three software elements plus one system prompt, and the scenarios that run across them.
* xref:L3-SE-01-input-client.adoc[L3: Input Client (SE-01)] is the visitor's phone screen: consent, the chat UI, alias and avatar, and how a turn is submitted.
* xref:L3-SE-02-display-client.adoc[L3: Display Client (SE-02)] is the projected wall: how recent exchanges are polled and laid out so they stay legible across the room.
* xref:L3-SE-03-backend-service.adoc[L3: Backend Service (SE-03)] is the one stateful service: the turn pipeline (gate, moderate, generate, persist), rate limiting, session policy, and the single outbound call to the language API.
* xref:L3-SE-04-system-prompt.adoc[L3: System Prompt (SE-04)] is the instruction set behind every Sparring reply. It has no runtime interface of its own but is modeled as a first-class element anyway.
